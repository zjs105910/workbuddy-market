# WorkBuddy 本机插件市场

参考 **DSH（DeepSeek Harness）的插件市场**做法，给 WorkBuddy 搭的一个**本机插件市场**：  
把你自己机器上的 skill 打包成标准插件，再注册进 WorkBuddy 自带的插件面板；  
同时附一个网页界面，用来浏览、搜索、一键装。

一句话：**双击 `一键启动.cmd` 就完事。**

> **本仓库不含 `plugins/`（打包产物），也不含任何人的市场配置**：市场内容是你本机 skill 的副本，属于个人数据，  
> 不随仓库分发；`market.config.json`（含你自己的 skill 组合）同样不入库，仓库只提供模板  
> `market.config.example.json`。运行状态、日志、所有权记录、回收站同样只留在本机。想要自己的市场内容，见[第四节](#四怎么改市场里的内容)：  
> `cp market.config.example.json market.config.json`，再把 `localPlugins` 指向你本机 `~/.workbuddy/skills/` 里的 skill；打包阶段会把「本机不存在的 skill」跳过，网页、收录源、自检一切照常。

## 一、怎么用（傻瓜模式）

| 我想…                       | 双击这个                     |
| ------------------------- | ------------------------ |
| 正常使用                      | **`一键启动.cmd`** ← 平时只用这一个 |
| 只想看网页界面，不想动 WorkBuddy 的配置 | `安全模式-只开网页.cmd`          |
| 不想要这个市场了，从 WorkBuddy 里摘掉  | `撤销注册.cmd`               |

`一键启动.cmd` 会依次做四件事，屏幕上都有中文提示：

```
[1/4] 打包本机 skill → 插件（增量同步）
[2/4] 自检
[3/4] 注册到 WorkBuddy 插件面板
[4/4] 打开市场界面
```

跑完会自动用浏览器打开一个本地网页（地址形如 `http://127.0.0.1:8777/`），  
**这个命令行窗口不能关**，关了网页服务就停了。按 `Ctrl+C` 或直接关窗口即可停止。

## 二、两种安装方式

### 方式 A：装进 WorkBuddy 的技能列表（原生形态）

`一键启动.cmd` 已经帮你注册好了——往 `~/.workbuddy/plugins/known_marketplaces.json`
加一条记录，写前自动备份，`撤销注册.cmd` 可随时摘掉。

装好后，skill 出现在 WorkBuddy 的 **「专家 技能·连接器」→ 技能页 → 「用户自定义」**
一栏，每张卡片带开关，和官方装来的 skill 一样用。

> **5.7.6 实测**：面板里**没有**「市场来源」下拉框，自定义市场不会以
> 「本机插件市场」板块单独露出——市场是幕后角色，技能页能看到它装的 skill
> 就说明它工作了。安装 / 卸载 / 更新走方式 B 的网页界面。
> 实测细节见 `docs/WorkBuddy-5.7.6-面板实测.md`。

### 方式 B：走网页界面

网页里有卡片，直接点按钮：

- **本机插件**卡片：
  - **「补齐」** —— 只把缺的 skill 复制到 `~/.workbuddy/skills/`，已有的不碰
  - **「更新」** —— 只有当「本市场装过、但之后被改过」的 skill 存在时才出现，  
    会把旧的先移进回收站再放新的（可回滚）
  - **「卸载…」** —— 先弹一个**分级预览**，告诉你哪些会移走、哪些会被保留，  
    确认后才动
- **GitHub 收录源**卡片 —— 点「一键安装」调用 `ghpm` 联网下载，  
  下方有实时进度条和 ghpm 的输出，装完自动刷新

顶部还有 **「回收站」** 按钮，能看到占用并可一键清空。

## 三、卸载为什么是安全的

这是 v2 最要紧的一处修改。**市场上架的 skill 和「本市场装过的 skill」是两回事**，  
只有后者才允许被卸载。

安装成功时，本市场会在 `.ownership.json` 里记下：

```json
{ "my-skill": { "owner": "wb-local-market", "plugin": "my-first-plugin",
             "version": "1.0.0", "installedAt": "...", "hash": "<内容指纹>" } }
```

卸载时按指纹分成三档：

| 分档      | 含义                  | 卸载时               |
| ------- | ------------------- | ----------------- |
| ✅ 可安全卸载 | 本市场装的，且内容没被动过       | 移入 `.trash/`，可恢复  |
| ⚠️ 被改过  | 本市场装的，但之后你改过        | **默认保留**，避免吞掉你的改动 |
| ⚠️ 非本市场 | 从别的途径装的（比如 ghpm 装的） | **永不触碰**          |

> 新机器上第一次用，点卸载什么都不会发生 —— 这是刻意的。  
> 只有「本市场装过」的 skill 才归它托管：把某个 skill 删掉、再从市场装回来，  
> 它才归本市场托管，那时卸载才会生效。

## 四、怎么改市场里的内容

只改一个文件：**`market.config.json`**（本机私有，已 gitignore）。克隆后先从模板复制一份，  
否则启动会明确报「market.config.json 不存在」：

```bash
cp market.config.example.json market.config.json
```

改完点界面上的「重新打包」，  
或重新双击 `一键启动.cmd`。

```jsonc
{
  "localPlugins": [
    {
      "name": "my-first-plugin",          // 插件 ID（也是目录名）
      "displayName": "我的第一个插件",      // 卡片标题
      "category": "工具",                  // 分类，界面按此筛选
      "version": "1.0.0",
      "description": "……",               // 卡片描述
      "keywords": ["示例"],
      "skills": ["my-skill", "……"]              // ← 要打包哪些本机 skill（按目录名）
    }
  ],
  "remoteSources": [
    {
      "repo": "anthropics/skills",        // GitHub 仓库 owner/repo
      "displayName": "Anthropic 官方技能集",
      "category": "官方",
      "description": "……",
      "skillCount": 19
    }
  ]
}
```

- **加一个本机插件**：往 `localPlugins` 里加一条，`skills` 填  
  `~/.workbuddy/skills/` 下的目录名。
- **加一个 GitHub 源**：往 `remoteSources` 里加一条，填 `owner/repo` 即可。
- **删掉插件**：从配置里删掉那一整块，重新打包。被删掉的插件目录会**rename 进  
  `.trash/`**，不会真删。

> 模板里的 `localPlugins` / `remoteSources` 默认为空：你装了什么、收录了什么，只存在于本机那份 `market.config.json` 里，不进 Git。

## 五、目录结构

```
workbuddy-market/
├── 一键启动.cmd                      ← 主入口，双击
├── 安全模式-只开网页.cmd              ← 不碰 WorkBuddy 配置
├── 撤销注册.cmd                      ← 从 WorkBuddy 摘掉本市场
├── _run.cmd                          ← 公共引导（找 Python），纯 ASCII
├── launcher.py                       ← 命令行入口与编排
├── market_core.py                    ← 内核：打包 / 注册 / 状态 / 安装（兼容入口，
│                                        实现自 v2.8 起陆续迁入 src/）
├── src/workbuddy_market/             ← 内核包（v2.8/R2 起）：paths / errors / fsutil /
│                                        hasher / locking / logging；v2.9/R3 增
│                                        config / scanner / sync / version
├── market_server.py                  ← 本地网页服务（只监听 127.0.0.1，带口令鉴权）
├── selftest.py                       ← 477 项自检（默认隔离模式，不碰真实环境）
├── market.config.example.json        ← ★ 配置模板（入库），先复制成下面那份再改
├── market.config.json                ← 唯一数据源（本机私有，已 gitignore）
├── .codebuddy-plugin/marketplace.json ← 市场索引（自动生成，WorkBuddy 读它）
├── plugins/                          ← 插件内容（自动生成，随你的配置而定）
│   └── <你的插件>/{.codebuddy-plugin/plugin.json, skills/…}
├── web/index.html                    ← 网页界面（单文件，服务端注入口令）
├── .ownership.json                   ← 谁装的、装时是什么内容 + 快速指纹（卸载靠它分级）
├── .market-tx/                       ← 安装/卸载的事务日志（正常结束即清空；残留会被自动补账）
├── .market.lock                      ← 跨进程写锁（Windows msvcrt / POSIX fcntl）
├── .market-log.lock                  ← 日志专用锁（只管轮转 + 追加）
├── .market-log.ndjson                ← 事件流，一行一条 JSON（超 10MB 自动轮转）
├── .market-state.json                ← 上次同步的统计
├── .backups/                         ← known_marketplaces.json 的备份（留最近 20 份）
└── .trash/                           ← 回收站（卸载 / 覆盖 / 退役的目录都在这）
    └── .index.json                   ← 各项体积记账，避免每次都重新扫一遍
```

## 六、命令行也行

```bash
python launcher.py --help         # 全部参数（argparse，冲突会明确报错）
python launcher.py                # 一键全流程（等价于双击）
python launcher.py --sync         # 只重新打包
python launcher.py --register     # 只注册
python launcher.py --unregister   # 撤销注册
python launcher.py --recover      # 只做事务恢复（补记上次没记完的所有权）
python launcher.py --recover --discard-conflicts  # 放弃那些「内容已被改过」的补账
python launcher.py --purge-trash  # 清空回收站
python launcher.py --status       # 状态 + 深度自检 + 回收站
python launcher.py --status --json    # 机器可读（CI / Harness 用）
python launcher.py --sync --quiet     # 只输出结果，不打印过程
python launcher.py --force-register # 打包/自检失败也照样注册（不推荐）
python launcher.py --no-register  # 只开网页，不碰 WorkBuddy 配置
python launcher.py --serve --no-open --port 8899   # 换端口、不开浏览器

python selftest.py                # 477 项自检，隔离模式（临时目录里跑完整流程）
python selftest.py --real         # 只读检查现网状态，不写任何东西
```

> **注意**：`一键启动.cmd` 在「打包」或「自检」失败时会**跳过注册**，但仍然打开网页。
> 注册会写 WorkBuddy 的配置文件，属于有外部副作用的步骤 —— 前置检查没过就不该动它，
> 否则 WorkBuddy 会看到一个「根本没更新成功的旧市场」，而你还以为启动成功了。
> 确实想强行注册就加 `--force-register`。

`selftest.py` 默认**在临时目录里**造 3 个假 skill，完整走一遍  
「打包 → 安装 → 更新 → 卸载 → 回滚 → 加锁 → 日志轮转 → 回收站清理」，  
**不碰真实的 `~/.workbuddy`，也不动真实的市场目录**。它覆盖了：

- 市场索引是否符合 WorkBuddy 原生 schema、`source` 目录与 `plugin.json` 是否齐全
- 打包排除、增量同步（增/删文件各只动 1 个）
- **同秒内 + 同大小的改动能被检出**（v1 的真实 bug）
- 安装三种模式、所有权记录、快速指纹快路径
- **卸载分级**：可安全卸载 / 被改过 / 非本市场，以及「用户自己的 skill 毫发无损」
- 文件锁的互斥与可重入、日志真 tail 与轮转、回收站按天数/容量清理
- 坏配置抛 `ConfigError` 而不是静默当成「配置不存在」
- 深度自检能否检出「版本不一致」「配置声明但未打包」
- 注册/撤销只动自己那一条、同一秒两次备份都留下

**第 16 节是故障注入**（v2.1 新增），专门验证「出错时数据还在」：

| 场景                             | 必须的结果                                        |
| ------------------------------ | -------------------------------------------- |
| 安装复制中途失败                       | 本机旧版本**内容与文件清单一字未改**，不留暂存目录                  |
| `known_marketplaces.json` 损坏   | register / unregister **拒绝写入**，坏文件原样保留       |
| 配置里写 `../escape`、`NUL`、`a/b` 等 | 15 种非法 id **全部拒绝**；越界 skill、插件重名、repo 格式错也拒绝 |
| 技能目录里放 junction / 软链指向外部       | **不被跟随**，外部文件名在市场里搜不到                        |
| `strict` 档位                    | 时间戳一样但内容不同 → **能检出**（fast 档位漏检，已作对照）         |

**第 17 / 18 节是第三轮评审新增的「构造对抗」用例**（v2.2）：

| 场景                                             | 必须的结果                                              |
| ---------------------------------------------- | -------------------------------------------------- |
| 改一个旧文件，**大小 / mtime / 最大值三者都没变**             | 指纹抓不到 → 但 install / uninstall **读内容后仍判 modified** |
| 连 mtime 都压回原值（指纹被完全伪造）                        | `update` **照样覆盖**（v2.1 会静默跳过）                      |
| 回收站索引里写 `../../外部目录`                           | `prune_trash` **不碰** `.trash` 外的任何东西                |
| 配置里同时写 `Story` 与 `story`                        | 全平台 `ConfigError`（Windows 上它们是同一个目录）               |
| 计划删 2 个、其中 1 个删失败                               | `removed=1 failed=1`，`freed` 只算 100 而不是 200          |
| `.index.json` 写入失败                           | 搬移**如实生效并成功返回**，下次状态刷新自动补录自愈                       |
| 市场产物里塞一个 junction                              | 安装**直接拒绝该 skill**，外部内容不进 `~/.workbuddy/skills`      |

**第 19 节是第四轮评审新增的「事务边界 + 本地 API」用例**（v2.3）：

| 场景                                   | 必须的结果                                          |
| ------------------------------------ | ---------------------------------------------- |
| 打包失败时跑 launcher                      | **不调用 `register`**，但网页照常启动；并如实告知跳过原因            |
| 全新安装成功、写 `.ownership.json` 失败        | 文件在盘上 + **留下事务日志**，安装仍报成功但给出告警；恢复后 skill 回到 `safe` |
| 更新成功、写所有权失败                         | 磁盘已换新，日志保留；恢复后所有权 hash 跟上新内容                    |
| 暂存阶段崩掉（日志残留）                         | 只清账、**不补记**、不动所有权                              |
| `register` 过程中 WorkBuddy 改了同一个文件     | 基于最新内容**重试合并**，中途写进来的条目没被覆盖                     |
| 配置写 `maxSizeBytes: 1.9` / `NaN` / `Infinity` | 一律 `ConfigError`（不再被 `int()` 静默截断）           |
| 没有口令 / 口令错 / `Origin: http://evil.example` | `GET`·`POST /api/*` 全部 **403**                 |
| 带正确口令 + 同端口 Origin                   | 正常放行 200                                       |
| `POST` 3 MiB 请求体                     | **413**（且不整段读进内存）                              |
| `POST` 坏 JSON                         | **400** 并说明是 JSON 解析问题                          |
| `/api/open/path` 传市场外路径 / `C:\Windows` | **400**，不弹资源管理器                               |
| `/api/open/path` 传 `target=plugin, id=../escape` | **400**                                    |
| job 表超过上限 / 已完成任务超时                   | 淘汰已完成的最老的；**运行中的一个都不动**                        |
| `/api/job/<id>/cancel`               | **真的杀掉子进程**（`poll()` 不再为 None）                |
| 1 秒内连续请求 `/api/state`                | 只重建一次（缓存）；有写操作则立即失效                            |


**第 20 节是第五轮评审新增的「事务闭环」用例**（v2.4）：

| 场景                                          | 必须的结果                                        |
| ------------------------------------------- | -------------------------------------------- |
| 事务日志都开不出来                                    | 安装**直接失败**，磁盘一个字节都不动                        |
| 崩在「`os.replace` 成功」与「交付确认」之间                | 凭证**已经存在**（v2.3 是 0 份），恢复据此认领                |
| 日志里带着 `expected hash` + `state`              | 恢复时靠它逐条比对，而不是看「目录在不在」                        |
| 崩溃之后、恢复之前用户改了文件                             | **拒绝认领**并报 conflict，保留日志；同事务里没被改的 skill 照常认领   |
| 同上，且跑了 `--discard-conflicts`                | 才放弃这笔账，**依然不认领**                             |
| 卸载时 `forget_owner()` 失败                     | 生成 `uninstall` 类型日志，恢复后补清所有权                  |
| 3 份日志共 22.9 MB，取最后 60 条                     | 只读 **32 KB / 1 ms**（v2.3 是读满 28.6 MB / 1378 ms） |
| `/api/remote/add` 传 `../../x` / `foo` / `-x/y` | **400**（复用内核的 `validate_repo`）                |
| 8 个并发请求同时撞上过期的状态缓存                          | `build_state` 只跑 **1 次**（single-flight）      |
| 目录形态的重解析点                                   | `_drop_link` **真的摘掉**它，目标目录毫发无损                |

**第 21 节是第六轮评审新增的「并发 / 扫描失败 / 崩溃点矩阵」用例**（v2.5）：

| 场景                              | 必须的结果                                       |
| ------------------------------- | ------------------------------------------- |
| 32 并发打 `/api/state`              | 无死锁、无异常；`build_state` **只重建 1 次**           |
| 8 并发 `install` / 8 并发 `register` | 无异常、无丢失更新、无重复事务                             |
| 10 个后台任务请求同时打进来                 | 只接受 `MAX_RUNNING_JOBS` 个，其余 **429**；令牌不泄漏    |
| 源端目录读不了                         | `sync` **直接失败**，市场内容**一个文件都不删**             |
| 安装源读不了                          | 该 skill 安装失败，本机版本**一个字节没动**                  |
| 本机 skill 读不了                    | 卸载判定保守当成 `modified` → **不搬走**                |
| 5 个崩溃点（tx_begin → record_owner 之间） | 恢复后 **disk ↔ ownership 一致、无残留暂存、日志收敛**    |

**第 22 节是第七轮评审新增的「ghpm 事件解析 / 取消竞态 / 进程树」用例**（v2.6）：

| 场景                                        | 必须的结果                                      |
| ----------------------------------------- | ------------------------------------------ |
| ghpm 发 `done/ok=false` 且**没有 error 字段**     | 不抛 NameError，任务行有兜底文案，**不会卡在 running**      |
| 同上但带 `error` 字段                           | 优先展示 error 原文                               |
| 取消发生在 `Popen` 之前                          | 直接返回 False，**不启动子进程**                       |
| 取消发生在运行中                                  | 子进程（连同它的树）被终止，任务收尾为失败                       |
| `MAX+6` 个请求**同时**打进来（barrier 真并发）          | 只接受 `MAX_RUNNING_JOBS` 个；满载计数 == 上限；结束后**槽位归零** |
| 全部用例结束                                    | `running_jobs() == 0`（并发槽不泄漏）、无卡死任务         |

> 隔离靠两个环境变量：`GHPM_MARKET_ROOT`（市场根目录）与 `GHPM_HOME`（WorkBuddy 家目录）。
> 少数用例依赖环境能力（比如能不能造出重解析点），造不出来时会打印 `SKIP` 并说明原因 ——
> **跳过不等于通过**，汇总行里会单独计数。

## 七、安全边界

这个工具会碰的文件就这几个，全都有备份或回收站兜底：

| 文件/目录                                          | 操作                         | 兜底                                              |
| ---------------------------------------------- | -------------------------- | ----------------------------------------------- |
| `~/.workbuddy/plugins/known_marketplaces.json` | 加/删**一条**记录，其余原样保留         | 全程持文件锁；**乐观合并**（写前重读比对，被别人改过就重试）；改前自动备份（纳秒戳）；写回后校验；`撤销注册.cmd` |
| `~/.workbuddy/skills/<name>/`                  | 安装只补缺 / 按需更新；卸载**只动本市场装的** | 全部走 `.trash/`，可手工拖回；装/卸全程有事务日志，崩了能补账                   |
| 本市场目录                                          | 打包产物，可随时重建                 | 退役目录也是 rename 进 `.trash/`                       |

> **关于 `known_marketplaces.json` 被改动**：WorkBuddy 自己在运行时也会改写这个文件  
> ——它会给 `autoUpdate` 的 zip 市场刷新 `lastUpdated`，并把 zip 地址换成带内容哈希的版本。  
> 所以如果你对比备份，看到那几个官方市场的时间戳变了，**那是 WorkBuddy 干的，不是本工具**。  
> 本工具严格「读最新 → 只动自己那一条 → 重读确认没被插手 → 原子写回 → 读回校验」，
> 不会覆盖别人的条目；万一撞车会自动基于最新内容重试。

- 网页服务**只监听 `127.0.0.1`**，不对外暴露。但 **localhost ≠ 只有你的页面能调用**：
  任何本机浏览器里打开的网页都能往这个端口发请求。所以从 v2.3 起：
  - 启动时生成一次性口令，注入到页面里；所有 `/api/*` 都要带 `X-Local-Market-Token`，否则 **403**
  - 带 `Origin` 的请求必须是本机同端口，否则 **403**（挡住跨源 CSRF）
  - 口令只存在于「服务端返回的那张页面」里；第三方网页读不到它 —— 跨源读响应被浏览器挡住
  - `/api/open/path` **只认白名单**：市场根、`plugins/`、`web/`、`.trash/`，以及指定 id 的插件目录。
    不再接受任意本机路径（v2.2 连 `C:\Windows` 都能开）
  - 请求体上限 1 MiB（超出 **413**），坏 JSON 明确回 **400**，不再静默变成 `{}`
- 所有写操作（打包 / 注册 / 安装 / 卸载）都在一把**跨进程文件锁**下串行，  
  不会出现两个进程互相覆盖（lost update）。
- 删除一律走「移入回收站」。**唯一会真删的地方是 `.trash/` 内部**，  
  而且只在超过 `market.config.json` 里的 `trash` 阈值时才动：  
  默认超过 30 天、或总量超过 2 GB 才清理。
- 日志超过 10 MB 自动轮转成 `.1` / `.2`，最多留两份，不会无限长。
- 打包会排除 `*.bak`、`__pycache__`、`.git`、`node_modules`、`*.pyc` 等  
  （见 `market.config.json` 的 `packaging` 段）。

## 九、常见问题

**Q：双击窗口一闪就没了？**  
说明 Python 没找到，窗口里会有英文提示（让装 Python 3.10+）。  
引导脚本会依次尝试 `py -3` → `python` → `%USERPROFILE%\.workbuddy\binaries\python\versions\3.13.12\python.exe`。

**Q：注册了但 WorkBuddy 插件面板里看不到？**  
先确认找的地方对不对：**5.7.6 实测**，面板（专家·技能·连接器）没有「市场来源」  
入口，自定义市场不会单独显示。装好的 skill 在 **技能页 → 用户自定义** 一栏。  
还看不到就重启一次 WorkBuddy，并用 `python launcher.py --status` 确认注册  
状态（应显示「已注册」）。安装 / 卸载 / 更新走 `一键启动.cmd` 的网页界面。

**Q：端口被占用？**  
会自动往后找 20 个端口。也可以 `python launcher.py --port 8899`。

**Q：我想把市场挪到别的盘？**  
整个目录搬走，然后重新跑一次 `一键启动.cmd`（会更新注册里的路径）。

**Q：点了卸载，怎么什么都没发生？**  
正常。说明这个插件的 skill **不是本市场装的**（是 ghpm 之类的途径装的），  
本市场不会去动它们。网页上会显示「非本市场 N · 不会动」。  
想验证：先把某个 skill 删掉，再从市场装回来，它才归本市场托管，那时卸载才会生效。  
如果你确实想移除那些 skill，用 `ghpm remove <项目名>` 或直接删目录。

**Q：怎么确认一切正常？**  
`python launcher.py --status`（含深度自检），或网页顶部的徽章。

## 十、v2 相对 v1 改了什么

v1 是我第一版（739 行）。一次代码评审提了 12 条，我逐条**先用探针验证再改**，  
下面是结果 —— 包括评审结论有偏差的地方。

### 先验证，再动手

| 评审的说法                              | 探针结果                                            | 结论                |
| ---------------------------------- | ----------------------------------------------- | ----------------- |
| `_sync_tree()` 每次全量扫描，一轮同步 3+ 遍遍历  | 实测 **28 次 `os.walk`、2119 次 `stat`、1 次 `rglob`** | ✅ 成立              |
| `int(st_mtime)` 精度砍到秒，同秒内同大小的修改会漏检 | 同大小、同秒内、晚 0.2 秒改写 → `_sync_tree` **拷贝数 0**      | ✅ 成立，是真 bug       |
| 卸载会误删「用户自己的」skill                  | 12 个真实目录会被全部移进 `.trash`，且无任何所有权记录               | ✅ 成立，最危险的一条       |
| 遍历次数是 `O(skill 数)` 的重复放大           | 实测每 skill 扫源一遍、扫目标一遍 —— 是常数 2，不是 N 倍            | ⚠️ 量级判断偏大，但重复确实存在 |

### 改了什么

**🔴 P0（正确性 / 安全 / 并发）**

- **mtime 改用 `st_mtime_ns`** —— 直接修掉上面那个漏检 bug。
- **安装记 ownership** —— `.ownership.json` 记录 owner / plugin / version / 内容指纹。  
  卸载按「可安全卸载 / 被改过 / 非本市场」三档处理，**最后一档永不触碰**。
- **install 支持 `missing` / `update` / `force`** —— 修掉  
  「市场显示 v2、本机还是 v1」的静默不一致；三种模式都不静默覆盖别人的 skill。
- **跨平台文件锁**（Windows `msvcrt` / POSIX `fcntl`，可重入）——  
  打包 / 注册 / 安装 / 卸载全部串行，消除 lost update。

**🟠 P1（性能 / 磁盘）**

- **单次遍历出索引** —— `_scan()` 一次走完就拿到「路径 → (大小, mtime_ns)」，  
  后面不再重复 `stat`；末尾那次全量 `rglob` 也去掉了。  
  **实测 stat 2119 → 1063，单次同步 0.35s → 0.13s（2.7×）。**
- **不再全树空转 `rmdir`** —— 原来不管有没有删文件，都对整棵目录树试一遍  
  `os.rmdir`。宿主/沙箱会给每个 `os.rmdir` 套一层路径校验，  
  **156 次空转 rmdir 就吃掉 0.32s**（profiler 实测）。现在只收「确实删过文件的那些目录」。
- **`atomic_write_text_if_changed()`** —— `plugin.json` / README / 索引 / 状态  
  内容没变就不写，省掉 fsync（实测 8 次原子写约 80ms）。
- **`tail_log()` 改真 tail** —— 用 `deque(fh, maxlen=N)`，不再整文件读进内存。  
  实测 20 万行日志取最后 10 条 **0.027s**。
- **回收站生命周期** —— `market.config.json` 的 `trash` 段配 `maxAgeDays` /  
  `maxSizeBytes`，超阈值才真删；`--purge-trash` 手动清空。
- **日志按大小轮转** —— 超 10 MB 转成 `.1` / `.2`，只留两份。

**🟡 P2（可维护性）**

- **`read_json(strict=True)`** —— 关键文件（配置、索引）坏了直接抛  
  `ConfigError` 并带上行列出错信息，不再表现成「配置不存在」。
- **`selfcheck()` 升级为 `deep_check()`** —— 四层一致性校验：  
  配置 ↔ 索引 ↔ 插件清单 ↔ 实际文件。能检出「版本不一致」  
  「配置声明了但没打包」，索引里多余的插件只报警告。
- **`_retire()` 与 `_trash()` 合并**成 `move_to_trash(path, reason)`。
- **备份时间戳加纳秒** —— 同一秒内两次备份也会各留一份（原来第二次会静默复用第一份）。

### 我自己在这轮里犯的错（也一并修了）

1. **市场当时是「镜像」不是「仓库」** —— 把某 skill 从本机删掉再打包，插件就从市场消失了，  
   「先卸载、再从市场装回来」根本走不通。改成：源不在了就**沿用市场里的历史副本**  
   并在报告里标成 `cached`。
2. **为了删空目录多加了一整遍遍历** —— 第一版改完 `os.walk` 从 28 涨到 42。  
   修掉后回到 28，同时 stat 仍然减半。
3. **`_line()` 没 flush** —— 管道下中间进度全攒着，看着像卡死。

### 评审里没做的一条

评审建议「维护一份文件指纹索引（含 sha256），之后只扫变化的目录」。  
这条我没做：当前规模（十几个 skill、几百个文件）单次同步 0.13s，  
引入一份需要保持一致的持久化索引，收益不抵复杂度。  
**什么时候该做**：本机 skill 涨到几百个、或单个 skill 有上万个文件时再说。

| `build_state()` 每次全量算 SHA-256        | 实测每次读 **5.7 MB**、耗时 **489 ms**                                              | ✅ 成立，非常严重  |


### 一个比评审说的更严重的问题：junction

评审只提了 symlink。我实测发现 Windows 上更隐蔽的是 **junction**：

```
_winapi.CreateJunction(...) → 成功
os.path.islink(link)        → False     ← 只看 is_symlink() 会完全漏掉
st_file_attributes          → 带 REPARSE_POINT
os.path.isdir(link)         → True      ← 于是被当普通目录递归进去
```

也就是说，只用 `is_symlink()` 判断软链是不够的，junction 会被当成正常目录遍历，  
把技能目录之外的**真实文件和内容**复制进市场目录。

**防护改成判文件属性位**（`FILE_ATTRIBUTE_REPARSE_POINT`），symlink 和 junction 一起挡。  
实测：技能里放一个指向外部目录的 junction，打包后**市场里既没有那个目录、也搜不到外部的文件名**。

> 诚实说明：本机的 `os.symlink` 被宿主环境拦成了普通空文件（`is_symlink()` 返回 False），  
> 所以**符号链接这一路我无法在本机实证**，只能实证 junction。软链的防护用的是同一段代码路径。

### 改了什么

**🔴 P0（正确性 / 数据安全）**

- **两阶段安装**（PREPARE → COPY → VERIFY → COMMIT → RECORD）：  
  先复制到 `.SKILLS_DIR/.<名>.installing-<pid>` 并校验，**校验通过才动旧版本**，  
  再 `os.replace` 原子换位；换位失败会把旧版本放回原位。启动时顺手清理上次的暂存残留。
- **`known_marketplaces.json` 严格读取**：写操作前文件读不出来就**直接抛错拒绝对付**，  
  并把备份位置告诉用户，绝不拿一个空表覆盖。
- **配置边界校验**：所有来自配置的名字先过 `validate_id`（拒绝 `..`、分隔符、盘符、  
  空白、Windows 保留设备名），拼出来的路径再过 `ensure_child` 兜底。
- **配置 schema**：检查插件重名、skill 被两个插件同时声明、repo 不是 `owner/repo`、  
  版本号非法、`trash` 阈值为负等，结构性问题在 `load_config()` 阶段就拦下。
- **软链 / junction 不跟随**：`_scan` 判重解析点，命中就跳过并计入报告。

**🟠 P1（性能）**

- **所有权加「快速指纹」**：装的时候同时记 `hash`（内容 SHA-256）和  
  `fingerprint`（文件数 / 总字节 / 最大 mtime_ns）。判断「有没有被改过」时  
  **先比指纹，只有对不上才去算哈希**。  
  实测 `build_state()` **489 ms → 25.6 ms（19×）**，且 **0 次文件读取**（每次刷新少读 5.7 MB）。
- **回收站索引**：`move_to_trash` 搬之前就把体积记进 `.trash/.index.json`，  
  `trash_stats()` 读索引而不是 rglob 整棵树。实测 **0.021 ms/次**。  
  手工往回收站拖的东西仍会被自动补录。
- **日志独立锁**：`.market-log.lock` 只保护「轮转 + 追加」，不跟业务主锁争。  
  拿不到锁时退化成无锁追加 —— 日志不该成为失败点。
- **`_scan` 改用 `os.scandir`**：`DirEntry` 的 stat 结果直接来自目录项、缓存着，  
  比 `os.walk` + `Path.stat` 少一轮按路径查询，还能顺手拿到属性位。
- **fast / strict 两级校验**（`packaging.verify`）：  
  fast（默认）比 size + mtime_ns；strict 连内容一起比，  
  能发现「改了内容又把时间戳改回去」。实测 strict 下「内容一样但时间戳不同」**不再重拷**。

**🟡 P2**

- **selftest 增加故障注入**（第 16 节），v2.1 时共 133 项
  （v2.2 → 178，v2.3 → 254，v2.4 → 304，v2.5 → 342，v2.6 → 353，v2.7/R1 → 384，
  v2.8/R2 → 410，v2.9/R3 → 439）。
- **日志事件带 `op` 字段**（operation id），便于把一次安装的多条事件串起来。

| 指标                      | v2               | v2.1             | 变化      |
| ----------------------- | ---------------- | ---------------- | ------- |
| `build_state()`（网页每次刷新） | 489 ms 且读 5.7 MB | **25.6 ms，0 读取** | **19×** |

**什么时候该拆**：再加两个功能域（比如「远端源的本地缓存」和「插件依赖解析」）时。

### 我这轮自己犯的错

1. **为了实现「只收空目录」多加了一整遍遍历**，`os.walk` 从 28 涨到 42（上一轮同款错误，

| ------------------------------- | --------------------------------------------------------------------- | --------------- |
| 快速指纹会「内容已改，但仍判 safe」            | 构造：旧文件改内容、**等长**、mtime 压回原值 → `fp_equal=True` / `hash_equal=False`    | ✅ 成立，是真实存在的误判   |
| `.trash/.index.json` 被篡改时越界删除    | 索引里写 `../../OUTSIDE-VICTIM` → `prune_trash(force=True)` **把市场根之外的目录删了** | ✅ 成立，实打实的越界删除   |
| Windows 下插件 / skill 名大小写冲突      | 配置里同时写 `Story` 与 `story` → 校验通过，两者指向同一个目录                              | ✅ 成立            |
| `move_to_trash()` 失败时事务语义不一致    | 读码确认：rename 成功后索引写失败会一路穿透，把整次安装判成失败                                   | ✅ 成立            |
| `prune_trash()` 统计虚报            | 构造「计划删 2 个、其中 1 个失败」→ 旧实现仍报 `removed=2`                                | ✅ 成立            |
| strict 模式大量 `read_bytes()` 吃内存 | **64 MiB 文件实测**：`read_bytes` 峰值 **64.0 MiB**，流式分块 **2.01 MiB**，耗时 44.9 vs 45.5 ms | ✅ 成立，且 CPU 几乎不变 |

### 改了什么

**🔴 P0（安全 / 正确性）**

- **快速指纹不再参与任何破坏性判定**。新增 `needs_exact(purpose)`：  
  用途分 `ui` / `install` / `uninstall`，只有 `ui` 允许走指纹。  
  `install`（决定是否覆盖）与 `uninstall`（决定是否搬走用户目录）**一律读内容算 SHA-256**。  
  同时把指纹从「文件数 / 总字节 / 最大 mtime_ns」扩成**再加一个 `mtime_ns_sum`** ——  
  常见场景（改动的文件 mtime 变了、但最大值由别的文件贡献）现在当场就能抓到。
- **`.trash/.index.json` 按不可信状态文件处理**。新增 `_trash_entry()`：  
  名字必须是单层 basename（拒绝 `/` `\` `:` `..` `.` 与索引自身），再经 `ensure_child`  
  钉死在 `.trash/` 内。`trash_stats()` 与 `prune_trash()` 都只能通过它拿路径；  
  非法条目直接剔除并告警，`deep_check()` 也会把它报成 error。
- **配置层大小写归一**。新增 `collision_key()`（= `casefold()`），插件名 / skill 名 /  
  远端 repo 全部按归一 key 判重，发现 `Story` vs `story` 直接 `ConfigError`。  
  **所有平台都拒绝**，不让 Linux 和 Windows 跑出两种行为。

**🟠 P1（事务 / 统计 / 内存 / 边界）**

- **`move_to_trash()` 的事务语义对齐现实**：rename 成功 = 磁盘状态已变，  
  此后索引写失败只记一条 warn 并**照常返回**，不再让整次安装被误判为失败。  
  丢失的只是记账，靠 `trash_stats()` 的「未登记项自动补录」自愈。
- **`prune_trash()` 统计不再说谎**：拆成 `removed` / `failed` / `freed`，  
  `freed` 只累加**真正删成功**的那些项；`rmtree` 的 `ignore_errors=True` 也去掉了  
  —— 原来它把失败吞掉，然后照样计入「已释放」。
- **SHA-256 全改流式分块**（`sha256_file()`，默认 1 MiB，可由  
  `packaging.hashChunkBytes` 调）：内存从 O(文件大小) 降到 O(块大小)。  
  `_same_content()` / `tree_hash()` 统一复用，不再出现 `read_bytes()`。
- **安装期链接防线闭环**：`copytree(..., symlinks=True)`，并且**源目录或暂存副本里  
  只要出现重解析点就直接拒绝安装**。打包禁止 → 市场产物禁止 → 安装再禁一次。
- **新增 `trash.protectModified`**（默认 `true`）：被标成「安装后被改过」的项，  
  在按天数 / 容量自动清理时会被跳过，只有 `--purge-trash`（force）才真的清。  
  自动清理不该悄悄吞掉用户的改动。

**🟡 P2（结构 / 维护性）**

- **打包时目标侧按插件只扫一次**，再用 `_sub_index()` 按 skill 前缀切片。  
  一个 12 skill 的插件：源 12 次 + 目标 1 次，而不是两边各 12 次。
- **配置升级**：`schemaVersion: 2`、`packaging.hashAlgorithm` / `hashChunkBytes`、  
  `trash.protectModified`；`packaging.verify` 新增 **`auto`**（默认值）。
- **版本号收敛**：`MARKET_VERSION` 成了唯一来源，README / 配置 / 代码 / 自检  
  都从它取。顺带把上一轮被写成「v3」的章节正名为 **v2.1**。

### 实测性能对照

| 指标                            | v2.1              | v2.2                        | 变化        |
| ----------------------------- | ----------------- | --------------------------- | --------- |
| 64 MiB 文件哈希峰值内存              | 64.0 MiB          | **2.01 MiB**                | **31×**   |
| 哈希耗时                          | 44.9 ms           | 45.5 ms                     | 基本不变      |
| 打包目录扫描次数（3 skill / 2 插件）      | 6 次（每 skill 源 + 目标各一） | **5 次**（源 N + 目标 1 / 插件） | 随 skill 数拉大 |
| selftest                      | 133 项             | **178 项**                   | +45       |

### 两处我记得很清楚的取舍

1. **`fast` 档位被我削弱了。** 评审推荐 `verify: "auto"`，但没说 `fast` 该怎么办。  
   我的选择是：`fast` 只影响「网页状态」，**不再能削弱 install / uninstall 的判定**。  
   也就是说，配置里写 `fast` 也不会再出现「本地已被改过、update 却跳过覆盖」——  
   这个档位从此只承担性能语义，不承担安全语义。
2. **架构拆分只采纳了一半。** 评审建议拆成  
   `inspect_skill()` / `decide_install()` / `decide_uninstall()` / `build_state()`。  
   我落成 `classify_skill(..., purpose=...)` 一个函数加一个 `inspect_skill` 别名：  
   调用点多、签名改动小，`purpose` 已经把「谁该精确」这件事表达清楚了。  
   真要按用途拆成几个函数，等它真的出现第三种用途再说。

## 十三、v2.3 相对 v2.2 改了什么（第四轮评审）

第三轮改的是「构造对抗」，这一轮的题眼是**事务边界**：  
现在「文件系统事务」已经很硬，但 `文件 + ownership + registry + job 状态`
还没有形成统一的事务模型。这一轮就是把这一层补上，顺带堵掉服务端的几个洞。

### 先验证，再动手

| 评审的说法                     | 我的探针结果                                                                     | 结论                 |
| ------------------------- | -------------------------------------------------------------------------- | ------------------ |
| launcher 失败后仍继续 register | 把配置写坏 → `[1/4]` 失败、`[2/4]` 失败，`[3/4]` **照样调用 register 并写盘**                 | ✅ 成立               |
| ownership 不是事务的一部分       | 全新安装 + 写 `.ownership.json` 失败 → 文件**装好了**、所有权缺失 → `classify_skill` 返回 **foreign** | ✅ 成立，**比评审说的更严重**  |
| （同上，更新路径）                 | commit 成功、ownership 失败 → 磁盘已换新，调用方看到异常，记录还停在旧 hash                          | ✅ 成立               |
| localhost API 没有 CSRF / 鉴权 | `Origin: http://evil.example` → install / uninstall / register / purge **全部 200 被执行**     | ✅ 成立               |
| `/api/open/path` 接受任意路径   | `C:\Windows`、用户家目录都被接受，explorer **连开 3 次**                                 | ✅ 成立               |
| `_body()` 没有大小限制          | 3 MiB 请求体整段读进内存；坏 JSON 静默变成 `{}`                                             | ✅ 成立               |
| `_jobs` 永久驻留              | 50 个已完成任务全部留在内存                                                             | ✅ 成立               |
| 安装过程重复 hash / scan        | 一次 update = `_scan` **6 次** + `tree_hash` 2 次                                  | ✅ 成立               |
| `/api/state` 每 skill 各扫一次  | 60 个 skill 的 `build_state` = **60 次目录遍历、2.2 秒**                                | ✅ 成立，量级确实吓人        |

### 改了什么

**🔴 P0（事务一致性 / 安全）**

- **ownership 纳入事务日志**。装 / 卸全程在 `.market-tx/` 写一份日志，  
  阶段是 `staging → committed → 收尾`，**每个 skill 换位成功就立刻登记**  
  （不是等整个循环跑完，否则中途崩掉时前面几个 skill 就没账了）。  
  收尾时一次性写所有权，写成功才清账；写失败就**保留日志并如实告警**。  
  下次打包 / 安装 / 卸载 / 启动时自动补记 —— 从「文件事务」升级成「文件 + 状态事务」。  
  `deep_check()` 也会把「已落位但没记所有权」报成 error。
- **launcher 的失败策略改成状态机**。打包或自检没过，就**跳过 register**（那条路径有外部  
  副作用），但网页照常启动 —— 页面是只读展示，能让你看到坏在哪。想强行注册有 `--force-register`。
- **本地 API 加鉴权**。启动生成一次性口令注入页面，所有 `/api/*` 校验  
  `X-Local-Market-Token` + `Origin`，缺失或跨源一律 **403**。  
  第三方网页即便知道地址也读不到口令（跨源读响应被浏览器挡住）。
- **`/api/open/path` 收紧成白名单**。只认 `target: root|plugins|web|trash|plugin`，  
  旧的 `path` 写法仍接受但必须落在市场根之内。最终都过一遍 `ensure_child`。

**🟠 P1（性能 / 生命周期）**

- **批量指纹扫描**：`build_state` 现在一次 `_scan(SKILLS_DIR)` 再按 skill 前缀切片。  
  声明少于 4 个 skill 时仍然逐个扫（整树扫反而更贵），阈值写在 `SkillScanCache.BATCH_SCAN_MIN`。
- **安装复用暂存索引**：`_stage_skill()` 把暂存副本的索引交出来，`record_owner()`  
  直接用它可以算出内容哈希与指纹，不再在 commit 之后把新版本重扫一遍。  
  顺带少了那次 `quick_fingerprint`。
- **job 加 TTL + 上限**：已完成任务保留 30 分钟后回收，任务表上限 100，  
  **运行中的任务永不淘汰**。`/api/job/<id>` 与新建任务时都会顺手清理。
- **ghpm 后台任务有超时和取消**：15 分钟看门狗 + `POST /api/job/<id>/cancel`，  
  终止时在 Windows 上走 `taskkill /F /T` 干掉整棵进程树（git / 代理 / 凭证助手都会留孤儿）。
- **`/api/state` 短 TTL 缓存**（1 秒），任何写操作后立即失效。

**🟡 P2（工程化）**

- **注册改成乐观合并**：`读 → 改 → 重读 → 比对 → 写`，被外部改动就基于最新内容重试（最多 4 次）。  
  v2.2 的「读 → 改 → 写 → 读回校验」只能发现「整个条目消失」，发现不了  
  「某个市场的字段被别人改了又被我们覆盖回去」。
- **`atomic_write(..., durable=True)`**：POSIX 上补一次父目录 fsync。  
  `ownership` / `known_marketplaces` / 事务日志用它，普通打包产物不用。
- **配置数值校验**：`maxSizeBytes: 1.9` 这类小数直接拒绝（原来会被 `int()` 静默截成 1），  
  `NaN` / `Infinity` 也拒绝。
- **顺带修掉一个自锁隐患**：`locked()` 每次调用都会 new 一个 `FileLock`，而重入计数是  
  **实例属性** —— 同一个线程在已持锁时再 `with locked():` 会拿另一个 fd 去抢同一段区域，  
  直接等锁超时。现在用一个线程级计数器把它变成真正可重入（`recover_transactions()`  
  之所以能在 `install` 内部取锁，靠的就是这个）。

### 两处我按自己的判断做了取舍

1. **没做模块化拆分**（评审的 ⑬）。确实到了该拆的体量（约 2700 行、13 个功能域），  
   但这一轮同时改了 12 处**行为**。把「结构性搬迁」和「行为修改」叠在同一轮里，  
   两边都会更难审 —— 而这一轮改的恰好是事务和安全边界，属于「必须能逐条验证」的改动。  
   更实际的理由：这轮**新增了「事务日志」和「服务端鉴权」两个功能域**，边界还在动，  
   现在拆很容易拆错。等这两个域稳定一轮，再按评审给的 `market/` 结构走，  
   `market_core.py` 留作兼容层。
2. **乐观合并只是「缩小窗口」，不是「消除窗口」**。WorkBuddy 不抢我们这把锁，  
   所以在「重读到 `os.replace`」之间理论上还有一个几十微秒的口子。  
   要彻底消除只能跟 WorkBuddy 约定同一把锁，那不在我们控制范围内。  
   我能做的是把它从「整个读-改-写过程」压到最小，并保留写回校验作为兜底 ——  
   这一点在 README 里如实写清楚，不假装它是完美的。

## 十四、v2.4 相对 v2.3 改了什么（第五轮评审）

v2.3 把「写所有权」纳入了事务，但只在**正常路径**上闭环。这一轮补的是
**异常路径上的最后一段**：凭证要早于磁盘变更，认领要校验内容，卸载要走同一套模型。

### 先验证，再动手

| 评审的说法                            | 我的探针结果                                                                       | 结论              |
| -------------------------------- | ---------------------------------------------------------------------------- | --------------- |
| `tx_begin` 创建得太晚                 | 在「commit 之后、tx_begin 之前」注入崩溃 → 磁盘**已换成市场版本**，事务日志 **0 份**                  | ✅ 成立            |
| 恢复「看到文件存在就认领」                    | 崩溃后让用户改一下文件再恢复 → 恢复把**用户的改动**记成了「市场装的、没改过」（`kind=safe`，hash 就是用户改完那份）    | ✅ 成立，比评审说的更严重   |
| 卸载没有事务                           | 让 `forget_owner()` 失败 → 目录**已被搬走**、ownership 还认着它、日志 **0 份**                  | ✅ 成立            |
| `tail_log` 名为真 tail，I/O 仍扫全文件     | 3 份日志共 22.9 MB，取最后 60 行**读满 28.6 MB、耗时 1378 ms**                              | ✅ 成立            |
| `/api/remote/*` 绕开已有 repo 校验      | 只判断「非空」，`../../x`、`foo`、`-x/y` 都能进后台                                          | ✅ 成立            |
| `/api/state` 有缓存击穿                | 8 个并发线程同时撞上过期 TTL → **8 次** `build_state()`                                  | ✅ 成立            |
| selftest `_drop_link()` 逻辑错         | `Path.is_dir()` 会跟随链接 → 对目录 symlink 走到 `os.rmdir(symlink)`（POSIX 上 ENOTDIR），链接摘不掉且异常被吞   | ✅ 成立（Windows 的 junction 恰好能 rmdir，所以本机没暴露） |
| selftest 版本号与代码不一致                | 头部写着 v2.2，内核已经是 v2.3                                                            | ✅ 成立，是我的疏漏     |

### 改了什么

**🔴 P0（事务闭环）**

- **凭证先于磁盘变更。** `tx_begin()` 提到循环之前；而且**在 `os.replace` 之前**
  就把「换位后应该长什么样」（expected hash + 指纹，`state="staged"`）写进日志。  
  这样「`os.replace` 成功 → 写日志」那个窗口里崩掉也有凭证。
  反过来，日志都开不出来时安装直接失败，磁盘一个字节都不动。
- **恢复要校验内容。** 认领条件是 `tree_hash(现在) == expected`，不是「目录还在」：
  - `state="staged"` 且对不上 → 这次交付本来就没完成，**静默放过**
  - `state="committed"` 且对不上 → 一定是崩溃后有人改过，记 **conflict**、  
    **保留日志**、写进 `deep_check()` 的 error。绝不把用户的改动洗白成市场版本。
  - 同一次事务里没被改过的 skill **照常认领** —— 逐条判决，不是一刀切。
  - 想放弃这笔账要显式 `--recover --discard-conflicts`。
- **卸载纳入同一套事务。** `pendingForget` 记「已搬进回收站、所有权还没清」的
  skill，`forget_owner()` 成功才清账；崩在中间也能补平，不再留下
  「文件没了、ownership 还认着它」的半截状态。

**🟠 P1**

- **`tail_log()` 换成真正的反向分块读**：从各文件尾部按 64 KB 往回读，凑够就停。
  实测 3 份日志共 22.9 MB 时，取最后 60 条从 **28.6 MB / 1378 ms** 降到 **32 KB / 1 ms**，
  而且成本不再随日志历史增长。
- **输入边界只留一处**：新增 `validate_repo()`，配置层与 `/api/remote/add|update` 共用。
  拒绝 `../`、单段、`-` 开头、超长、空白、控制字符。
- **`/api/state` 加 single-flight**：TTL 过期瞬间只让一个线程去重建，其余等它。
  实测 8 个并发请求 → `build_state` 只跑 1 次。
- **HTTP 加固**：连接读写超时 15 秒（防慢连接占线程）、接收队列 32、线程随主进程退出。

**🟡 P2**

- **launcher 换成 argparse**：互斥动作、非法端口、冲突参数都有规范报错和 `--help`。

### 顺手修掉两个我自己的疏漏

1. **`_drop_link()` 用 `Path.is_dir()` 判断类型** —— 它会跟随链接，对「指向目录的
   symlink」会走 `os.rmdir(symlink)`，POSIX 上直接 ENOTDIR，链接摘不掉，异常还被
   `except OSError: pass` 吞掉。Windows 的 junction 恰好能 rmdir 成功，所以本机一直
   没暴露 —— 但它会污染后续用例（残留的链接让「链接安全检查」拒绝本该成功的安装）。
   改成 `lstat` 判断。
2. **selftest 头部版本号停在 v2.2** —— 代码已经是 v2.3 了。已升到 v2.4，并**加了一条
   用例专门盯这件事**：`SELFTEST_VERSION` 必须等于 `MARKET_VERSION` 的前两段。

> 顺带更正一处说法：README 第十节把 v2 的 `deque(fh, maxlen=N)` 写成了「真 tail」。
> 它只省了内存，**I/O 仍然是整个文件** —— 名不副实，这一轮才真正做对。

### 一处我明确保留的设计

**conflict 不会自动消解。** 我本可以让「冲突时以磁盘内容为准、写成一条 modified

## 十五、v2.5 相对 v2.4 改了什么（第六轮评审）

这一轮的主题从「再加安全补丁」转到**并发边界与 I/O 路径**。评审 6 条全部探针复现后落地。

| 评审的说法                        | 我的探针结果                                                     | 结论   |
| ----------------------------- | --------------------------------------------------------- | ---- |
| SingleFlight 超时/异常路径会击穿       | leader 抛异常 + 6 并发 → `build_state` 被调 **6 次**               | ✅ 成立 |
| `MAX_JOBS=100` 不是并发上限          | 连开 140 个 running 任务 → 表里真留 140 个，每个一条线程 + 一个子进程            | ✅ 成立 |
| `_scan` 遇 OSError 静默跳过         | 同步里一次读取抖动 → 源端「少看见」的文件在目标端被判多余 → **删掉 2 个市场文件**            | ✅ 成立，最危险的一条 |
| SkillScanCache 扫整棵 skills 树    | 市场 6 个 skill 却扫 406 目录 / 2842 文件，223 ms                   | ✅ 成立 |
| `_sub_index` 每 skill 遍历全索引    | 6 个 skill = 17124 次迭代                                     | ✅ 成立 |
| 回收站索引逐次落盘                    | 连续装/卸 N 个 = 「读-改-原子写」× N                                  | ✅ 成立（批量大时才明显） |

### 改了什么

- **SingleFlight 改成共享结果盒**：value / error 都由 leader 填，等待线程直接取，
  超时与异常路径同样只跑一次。
- **`MAX_RUNNING_JOBS=4` 并发闸门**：创建任务前抢信号量，抢不到直接 429；
  worker 无论成败都在 `finally` 里还令牌。`MAX_JOBS` 降级为纯历史表上限。
- **扫描 fail-closed**：`_scan(..., on_error=)` 显式区分「展示」（skip）与
  「破坏性操作」（raise `ScanError`）。`_sync_tree` 两侧一律 raise ——
  宁可整次同步失败也不误删；安装循环里单个 skill 失败只影响那一个。
- **批量扫描只走声明的 skill**（`_scan_many`），扫描时按名字分桶：
  223 ms → **72 ms**，`fingerprint(name)` 变成 O(1) 取桶。
- **`TrashIndex` 整批只落一次盘**：索引提到内存，批量装/卸做完统一 flush。
- launcher 加 `--json` / `--quiet`。
- **模块化拆分继续缓行**：事务边界刚定型，同轮既改行为又搬结构会让两边都更难审。

### 顺带补记

这一节的 README 是 v2.6 轮补写的 —— v2.5 当轮改了代码、docstring、selftest
（304 → 342 项）和本节前后的计数，唯独漏了这节正文。第 21 节的用例表当时已就位。

## 十六、v2.6 相对 v2.5 改了什么（第七轮评审）

v2.5 之后核心设计已经扎实，这一轮收的是**后台任务生命周期的两个边角**：
一个真 bug（`label`），一个测试本身没真正模拟并发。

### 先验证，再动手

| 评审的说法                              | 我的探针结果                                                          | 结论       |
| --------------------------------- | ------------------------------------------------------------- | -------- |
| `_run_ghpm()` 里 `label` 未定义        | 伪造 ghpm 发 `done/ok=false` 无 error 字段 → **`NameError: name 'label' is not defined`**，异常冒到 worker 后 `_job_finish` 不跑，任务永远 running | ✅ 成立     |
| 并发自测是串行调用，不是真并发                    | 串行发起 MAX+6 个任务、ghpm 秒失败 → 10 轮里 **10/10 轮 accepted 超限**（上限 4，accepted 全是 10）。此前全量自检能过纯属真实 ghpm 失败得稍慢 | ✅ 成立     |
| POSIX `kill_process_tree` 只 terminate 父进程 | 读码证实：`else: proc.terminate()`，git/凭证助手会变孤儿                      | ✅ 成立     |
| 取消与 `Popen` 之间有窗口                  | 读码证实：`Popen` 与 `job["proc"]` 赋值之间 cancel 杀无可杀，只能靠 0.5s 后的看门狗兜底  | ✅ 成立     |
| `running_jobs()` 读 `Semaphore._value` | 读码证实（当时靠 `# noqa` 压警告）                                        | ✅ 成立     |

### 改了什么

**🔴 P0**

- **失败事件兜底**：`done/ok=false` 时显示 `error` 字段，其次 ghpm 自带的 `label`，
  最后兜底「ghpm 执行失败」—— 不再有 NameError，任务正常收尾。
- **并发闸门测试改真并发**：barrier 让 MAX+6 个请求同时出发，gate 挂住假 ghpm
  保证满载可观察。断言三件事：接受数 == 上限、满载计数 == 上限、结束后槽位归零。

**🟠 P1**

- **POSIX 真杀整棵树**：ghpm 子进程改用 `start_new_session=True` 启动
  （pgid == pid），取消/超时走 `os.killpg(SIGTERM → SIGKILL)`；不在进程组的老
  情况退回单杀。Windows 的 `taskkill /T` 路径不变。
- **取消竞态两处收口**：`Popen` 之前先查 `canceled`（不白白拉起进程）；`Popen`
  之后把 proc 挂上 job 时再查一次 —— 若 `cancel_job` 恰好落在中间，由这里补杀。
- **`JobLimiter` 取代裸信号量**：闸门与运行计数由同一把锁保证一致，
  `running_jobs()` 不再碰 `BoundedSemaphore._value`。以后想把「超限拒绝」
  升级成「排队」只改这一个类。

### 评审里我暂缓的两条（记录在案）

- **job 状态机**（queued/starting/…/timeout）：值得做，但要同步改前端对
  `status/ok` 的契约，放到下一轮单独做，不和 bug 修复混在一轮。
- **全局 invariant 断言框架**：本轮已把「并发槽归还」「无卡死任务」作为不变量
  嵌进并发用例；完整框架随状态机一起做。

## 二十、v2.10 相对 v2.9 改了什么（GitHub 动态目录）

**这轮解决的问题是**：收录源的 stars / 更新日期是手工写进配置的快照，会过期；
搜索框只能搜市场里已有的条目，GitHub 上有而市场没收录的项目无法触达。
参考 DSH 市场的「精选目录承担静态身份 + 动态数据每日刷新」分层（其做法是远端 CI
每天重建 `plugins.json`），本市场是本机服务，直接用一个后台线程把这件事做了，
不需要任何外部基础设施。

### 新增了什么

- **`src/workbuddy_market/catalog.py` 新模块**：GitHub 实时元数据（stars /
  pushed_at / 描述 / 语言 / 归档状态）+ 全网搜索。网络接缝只有 `_gh_request()`
  一处，自检 monkeypatch 它离线测完全部逻辑。
- **每日自动刷新**：`serve()` 起 daemon 线程，每 15 分钟检查一次，条目超过
  24h TTL 就逐个重拉（全新鲜时零网络）。`WBM_CATALOG_OFF=1` 可关。
- **网页**：
  - 收录源卡片显示实时星数与「更新于」日期；区块标题显示目录刷新时间，
    附「刷新目录」按钮（走后台任务，可看进度、可取消）；
  - 搜索框在本地零匹配且关键词 ≥2 字时，自动搜索 GitHub 全网（600ms 防抖），
    结果卡片可直接「一键安装」——非收录仓库的确认框会额外提示「不在精选收录里，
    安装前请确认来源可信」。安装链路完全复用 ghpm 的事务 / 回滚 / 进度 / 超时。
- **三个新接口**（全部过 `_guard()` 口令 + Origin 校验）：
  `GET /api/catalog`、`GET /api/gh/search?q=`（词长上限 + 120s 内存缓存 +
  single-flight）、`POST /api/catalog/refresh`（走 JobLimiter，满员 429）。

### 容错口径（统计要诚实，约定 5）

- 单个仓库拉取失败 → **保留旧值**，错误记进 `errors`，网页卡片显示「刷新失败」；
- 整轮全部失败 → **不更新 refreshedAt**——失败不算「刷新过」，自动循环才会
  按条目 TTL 继续重试，而不是傻等 24 小时；
- 缓存文件（STATE_HOME 的 `catalog.json`）损坏 → 当不存在，绝不炸状态页；
- 自动循环的闸门是**按条目**的 TTL，不是整份目录的 refreshedAt——否则个别
  条目连续失败时，整份目录看起来永远新鲜，那个条目就再也轮不到重试。

### 与 provider 协议的关系

按 `docs/protocol/provider-api.md` 设计稿的口径落地：**易变数据永不写回
`market.config.json`**。`remoteSources` 里手工填的 `stars` / `verifiedAt`
退化为「上次的快照」，展示层优先用实时值；完整的多来源 Provider 抽象
仍按计划排在 R4 之后。
