### Session pickup

**You own the resume point. Read the prior trail, don't redo it.**

1. Locate the prior trail. It is a T3 thread, a pushed branch, or a worktree, per [the runtime's History section](../../pstack-runtime/SKILL.md#history). For a thread, find it with `t3_thread_search` (topic, branch, or PR number) unless the user attached or named it, then read it with `t3_thread_read`. Read `view: "messages"` from the last messages back to the decision points, and `view: "activity"` for the tool calls that changed state. Child task threads hold the delegated work, so follow each `childThreadId` the trail names and read that thread too. Search stays inside the current project. Do not read threads from unrelated projects unless the user attached them. For a worktree or branch, `t3_worktree_list` (with `query` set to the branch) gives its checkout path, `t3_thread_read` on a candidate thread returns that thread's `worktreePath` and `branch`, and `t3_worktree_status` reports whether this thread is bound to a worktree. Read uncommitted state with `git -C <path> status` and `git -C <path> stash list`. Check for a resume note from `playbooks/pause-safely.md` (`.pstack/resume/<slug>.md` in the worktree, or the path its last message names) and read it first. Parse a long thread in a child task and keep the reduced timeline in the main thread (the **principle-guard-the-context-window** skill).
2. Reconstruct operational state. The branch and worktree, any schedule the prior work owns (`list_scheduled_tasks`), the PRs the prior thread linked (`list_thread_pull_requests` with the `threadId` of the thread step 1 found, and also with the `threadId` on the resume note's `Writer thread:` line when that names another thread), the pull request URLs under `Paused pull request watches` in the resume note, what already landed (`git log`, `git diff` against the base), the open todos, the decisions made. The prior trail is authoritative input. Resist the bias to re-derive it.
3. Diff done vs pending. Compare what shipped against what was planned, name the resume point, do not re-run the prior repro or redo completed work. A "let me verify from scratch" pass means you're treating the trail as untrustworthy when it's authoritative.
4. Route the remaining work to the matching playbook and pick the verdict: continue the execution, ship a finished recommendation, ratify or override a prior conclusion, or postmortem a failed run. When the verdict is to continue the execution, call `link_pull_request` on each pull request from the combined step 2 list whose state is open and that the resumed work keeps driving. Then call `watch_pull_request` on each URL under `Paused pull request watches` in the resume note whose state in that combined list is open, per [Pull request watching](../../pstack-runtime/SKILL.md#pull-request-watching). Restore only those URLs. A missing heading, or a `None.` line under that heading, restores no watch. After the `watch_pull_request` calls, or when the verdict is not to continue the execution, replace the list under that heading with `None.` and clear the `Writer thread:` line, so a URL cannot outlive the pause that wrote it. The pickup playbook ends here. The routed playbook owns the rest.
5. Verify the inherited claims against the original goal on the real artifact (the **principle-prove-it-works** skill). A passing prior self-report is not the proof.

**Reply:** where the prior agent stopped, what you inherited vs redid (ideally nothing redone), each pull request you linked, each pull request you watched again, the resume point, and the outcome.
