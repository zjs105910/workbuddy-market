### Autopilot-full

**You own the verdicts, never the PRs. One owner runs each PR from build to merge, and nothing merges without your clean swarm verdict.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. Orchestrate runs a standing program whose coordinator lands verified work itself and whose workers never merge. Here each PR's owner carries the whole lifecycle through the merge, and the root keeps only verification, countersigns, and audits.

[The runtime's Modes section](../../pstack-runtime/SKILL.md#modes) sets the mode lines of every brief this playbook writes and how its spawns run in light mode.

1. **Mark the operator's items and honor state-then-wait.** Items the operator names stay with the operator. The operator reviews and clicks, and no owner merges one. When the operator asks for the protocol or the plan to be stated, deliver the statement and stop. Execution starts only on the operator's explicit go.
2. **Spawn one owner per PR with the full lifecycle and an early trail.** Resolve the forge once for the program. GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr ...` for PR create, edit, view, watch, and merge operations. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One owner per PR owns the lifecycle. Each owner is a top-level thread from `t3_thread_launch` with a worktree `workspaceStrategy` and a `modelSelection` from the item's code role, per [the runtime's Top-level threads section](../../pstack-runtime/SKILL.md#top-level-threads). Invoking this playbook is the user's request for those threads. Its `message` opens with the poteto-agent persona per poteto-mode's Subagents section. Retain each `threadId`. Each owner brief carries the root's thread ID. Each owner `message`, including a replacement's, carries the mode lines and the seat rule from [Resolve and carry the mode](../../pstack-runtime/SKILL.md#resolve-and-carry-the-mode). The owner sends the root one-line messages with `t3_thread_send` and `mode: "auto"`, because a launched thread does not wake its launcher per [Top-level threads](../../pstack-runtime/SKILL.md#top-level-threads). Those lines are `CODE-READY <pr> <head>`, `MERGE-READY <pr> <head>`, `MERGE-PREP <pr> <head>`, and `MERGED <pr> <sha>`, where `<sha>` is the squash commit on trunk. A later head that changes the patch is another `CODE-READY` line. The root sends verdicts and fix requests to the owner with `t3_thread_send` and `mode: "auto"`. The owner carries build, the first push, a ready PR, self-proof on the real artifact (the **prove-it-works** principle skill), skeptical Bugbot triage per `../references/bugbot-triage.md`, a slop-strip (the `deslop` skill (`/deslop`) if installed, otherwise a manual pass over the diff per the **unslop** skill), `/no-comments` (the **no-comments** skill), a rebase onto current trunk, the babysit loop to green (`playbooks/babysit.md`), which waits with `watch_pull_request` on this owner thread per [Pull request watching](../../pstack-runtime/SKILL.md#pull-request-watching), and the merge itself. Within about 15 minutes, every owner starts a `decisions.tsv` trail per the **show-me-your-work** skill, pushes its first branch snapshot, opens the PR ready, never draft, and links it with `link_pull_request`. That target orders the work and never waives the item's How, Architect, or code-delegation steps before `CODE-READY`, per [the runtime's Deadlines section](../../pstack-runtime/SKILL.md#deadlines). After that, the owner pushes its branch again after every verifiable unit (hooks on, a WIP commit is fine). Open the PR before self-proof so the URL, decisions, and checks form a durable trail. Keep `decisions.tsv` uncommitted and return it with the reports. As soon as a subagent starts, the owner adds its `taskId`, its `childThreadId`, expected runtime (at least the longest past run of that kind), and state to a `children.tsv` kept the same way. The owner does the first rebase before the `CODE-READY` message and babysit, whether or not trunk has drifted. In fix rounds, the owner keeps that merge base. The owner rebases again only at merge prep (step 5), on a `git merge-tree` conflict with trunk, or on a CI failure that comes from a change on trunk. When the shipped code is final, after the slop-strip and `/no-comments`, it sends `CODE-READY <pr> <head>`. It also sends `CODE-READY <pr> <head>` for each later push that changes the patch. Self-proof, CI, and babysit then run in parallel with the swarm. The owner sends `MERGE-READY <pr> <head>` when self-proof, CI, and babysit finish. Before a push that starts a round, run the pre-review checks that the repo's AGENTS.md files and rules name for the touched paths. Run them on the committed head. A hook pass is not proof. To publish each rebase, push the owner's own branch with `git push --force-with-lease` after an `ls-remote` check. Never force-push a shared branch. The merge is the one step an owner may not take alone. Step 4 gates it.
3. **Run owners in true parallel and never stack.** Many owners at once when PRs are self-contained: one writer per branch, disjoint files, cross-PR drift absorbed by rebase. Only genuinely overlapping work serializes. Owners run in parallel, but their builds and tests share this machine. Each owner `message` and each step 4 lane brief requires local builds, tests, and verifier reruns through `land.py slot --` per [the runtime's Local command capacity section](../../pstack-runtime/SKILL.md#local-command-capacity). Self-contained PRs branch straight off main, and sequenced work is merge-then-branch. One exception: an owner that must split a genuinely dependent change may hold a short private base-branch stack.
4. **Swarm-verify every round before its merge.** A round starts at the head in a `CODE-READY` message and at each later `CODE-READY` head that changes the PR's patch. At that SHA, fan out parallel independent verifiers per the **swarm** skill, seated from the `verifiers` role on a model family other than the owner's when one is runnable (a different provider can serve the same family, so compare models, not providers), and aggregate to one verdict. The merge needs a clean verdict from the round whose patch matches the head in `MERGE-READY`. Audit the receipts for the head in the `MERGE-READY` message before the verdict. The lanes: re-run the gates at that SHA. Prove the load-bearing behavior live on the real surface the change touches (with the matching control skill, such as `control-cli` or `control-ui` if installed, otherwise the terminal or T3's preview tools per [the runtime's Verification surfaces](../../pstack-runtime/SKILL.md#verification-surfaces), or a named driver where none exists). Audit the diff, distrusting the PR body. Run the audit as two or more review lanes with the full brief. Give each lane one main focus, such as consumer parity with trunk, lifetimes and races, or data and config safety. **Regression lane against trunk.** Run the same load-bearing scenario on current trunk. If trunk does not have the feature, record that fact and gate the behavior the diff adds plus the end state the user waits for instead of pretending trunk can produce it. The live lane is the floor, and a verdict without it is not clean. No merge without the root's clean verdict. When the lanes return, send every proven finding against the PR to the owner in one fix-forward with `t3_thread_send` and `mode: "auto"`. A defect that a lane filed as a note is a finding. For each behavior finding, ask for a red test that covers every site with the same defect. Where no test can show the defect, ask for a repro receipt instead. Add that defect to the next round's review brief. The new head gets a fresh swarm and a fresh verdict, except for lane results that stay valid under the patch-id rule in `playbooks/shipping.md`.
5. **On a clean verdict the owner merges, and a fresh owner takes the next item.** The owner merges only from a head freshly rebased onto trunk. Merge prep never comes before a round's lanes start, and it ends with a rebase onto current trunk right before the merge. After the merge-prep rebase, the owner sends `MERGE-PREP <pr> <head>`. On `MERGE-PREP <pr> <head>`, the root compares the new head's `git patch-id` with the verdict's under the patch-id rule in `playbooks/shipping.md`. The root keeps the verdict when the patch-id matches, and keeps each lane that rule still allows. The root starts a fresh round when the patch-id does not match. The root requires CI on the current head before the owner merges. An earlier readiness message cannot stand in for that CI. The owner calls `watch_pull_request` per [Pull request watching](../../pstack-runtime/SKILL.md#pull-request-watching) and ends the turn. Once that head is green and its patch-id matches the verdict's under the patch-id rule in `playbooks/shipping.md`, a later trunk move does not force another rebase. Right before the merge, fetch trunk and check that `git merge-tree` of the head against current trunk is clean. Also check that no path in `git diff --name-only $(git merge-base HEAD origin/main) origin/main` is a path the PR changes or a path that decides which CI runs for it, such as the repo's CI config paths. If either check fails, rebase again, send `MERGE-PREP <pr> <head>`, call `watch_pull_request` per [Pull request watching](../../pstack-runtime/SKILL.md#pull-request-watching) and end the turn until CI passes on it, and repeat these checks. A new head voids the verdict unless the patch-id is unchanged. The owner squash-merges its own PR through the resolved forge, sends `MERGED <pr> <sha>` for the squash commit on trunk, and returns. On `MERGED <pr> <sha>`, the root records the squash commit and advances the queue to the next item. A fresh owner, a new `t3_thread_launch` thread, picks up that next self-contained item, per poteto-mode's Subagents section. The operator's full-autonomy grant plus the root's clean verdict is the merge authorization that babysitting alone never has. Operator-named items stop after sending `MERGE-READY` and wait for the operator's click.
6. **Run the root layer.** A genuinely new raise of a pinned gate or budget value (a limit CI only lets tighten) needs your fresh countersign, granted only after verifier proof. If the operator's grant or standing orders cover approvals, that countersign is the approval. The owner records it in the form that the tool's approval contract allows, with a pointer to the root's countersign. A lane checks the record against that countersign. The root never gives or bypasses an approval that the forge enforces. Absorbing values that already landed on main is drift, not a raise. Run an audit tick over all owners every hour. On the operator's go, arm `schedule_task` with `{"type": "interval", "everyMs": 3600000}` and a prompt that runs this tick and points at the owner list and the collected decision trails, per [the runtime's Scheduling section](../../pstack-runtime/SKILL.md#scheduling). Report its `nextRunAt`. Never leave the cadence to memory or lossy completion notifications. At each tick, re-read this playbook in full from its installed path, `<skills>/poteto-mode/playbooks/autopilot-full.md`, where `<skills>` is the absolute pstack skills directory the tick prompt records, and audit the operation against it. Fix drift during that tick. Probe each owner thread with `t3_thread_read` and `afterPosition`, and each owner's subagents with `t3_thread_read` on the `childThreadId` values in its `children.tsv` (the root does not own them, so `task_status` does not apply), and collect the decision trails. Count only side effects as progress: commits, pushes, PR or check deltas, and store reports. Treat a lane that errors, or that passes its expected runtime without a side effect, as stuck. Stand it down and dispatch a replacement at once. Do not wait for a polite return. The tick judges an owner by the pushed branch and the decision trail that step 2 requires, and it replaces an owner whose agent cannot start a turn. Each tick also runs the lane stuck test over the program's thread list from `t3_thread_list`, and over every owner's `children.tsv`. Whether or not a stop works, the root has the owner record each stuck subagent as stuck and, if its work is still needed, replace it. Each replacement that stalls gets the same steps. The root cannot call `task_status` or `task_cancel` on an owner's subagents, because T3 scopes those to the thread that delegated them. The root reads a subagent's progress with `t3_thread_read` on its `childThreadId` and stops it with `t3_thread_interrupt` on that thread. When the owner cannot act, the root interrupts the stuck subagent that way, records it in `children.tsv`, and has a fresh owner replace it. A stall never proves or drops the work. When merges batch, run a retro pass and a post-merge bot-comment sweep. Delete the tick schedule with `delete_scheduled_task` only when no delegated work is left, even after the last merge.
7. **Stand down instantly on the operator's stop.** A queued message does not stop a running turn, so the root calls `t3_thread_interrupt` on every owner thread first, then sends the zero-writes hold with `t3_thread_send` and `mode: "restart"`. Each owner's first act on the hold is `task_cancel` on every live subagent in its `children.tsv`. The root confirms with `t3_thread_read` that no owner or subagent is still running and interrupts any that are. Owners hold their briefs until the operator releases them.

**Reply:** the queue with each PR's owner, state, and head SHA. Each verdict and the swarm that produced it. What merged and what each fresh owner took next. Countersigns granted and why. Open operator gates. Where the collected decision trails live.
